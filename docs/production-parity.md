# Production parity checklist

Production parity means the platform is ready for a broad commercial launch, not merely that one model returns successful responses. Every control below requires an implementation, an automated test or reproducible drill, an owner-facing runbook, and live verification.

| Capability | Current state | Exit criteria |
| --- | --- | --- |
| API contract, login, key lifecycle, billing | Complete | OpenAI-compatible requests, fail-closed privacy routing, expiration/revocation, hard spend limits, idempotent settlement, and live smoke tests remain green. |
| Edge and origin security | Complete | Managed TLS, Cloud Armor, direct-origin blocking, rate-based abuse bans, authentication-spike alerts, and documented threshold tuning. |
| Customer auditability | Complete | Metadata-only key and inference events, JSONL/CSV export, retained backups, tenant-isolation coverage, CSV-injection defense, and a live managed-key canary are verified. |
| Backup and recovery | Complete | Seven-day PITR, daily retained exports, backup-failure alerting, and an isolated restore drill with measured RPO/RTO and verified cleanup are in place. |
| Multi-region control plane | Complete | At least two gateway regions behind health-based routing with no shared regional single point of failure and a documented failover drill. us-central1 + us-east4 gateways behind the global edge, multi-region (nam7) Firestore, per-region Redis and per-region confidential model clusters, and passed failover and Redis-loss drills. Redis failure fails open (rate limits/admission only) and `/readyz` gates on Firestore, so a regional dependency loss degrades rather than fails the region. |
| Model rollout safety | Complete | Digest-pinned model revisions, readiness and quality gates, canary traffic, automatic rollback, and version-visible responses. Model images deploy only by digest through `scripts/model_rollout.sh` (off-service canary with golden-prompt gates, health-gated promotion that never drops serving capacity, automatic rollback), responses stamp `x-model-revision`, and both a good and a broken rollout were drilled live with zero failed customer requests. Quality gates are smoke-level golden prompts; a scored eval suite is future hardening. |
| Capacity and admission control | Partial | Reserved or diversified GPU capacity, concurrency queues, overload responses, capacity alerts, and tested scale/failure behavior. Done: global per-backend admission control over Redis (503 + Retry-After before billing, live-tested at exactly the configured bound), alerts for sustained overload, backend failures, and the gateway instance ceiling, and autoscaled surge behavior exercised by the rollout drill. Remaining: GPU capacity is neither reserved nor diversified (the confidential GPU pool is a single dedicated node class). |
| Verifiable confidential compute | Partial | Client-verifiable attestation bound to workload and model image digests, freshness, documented verification, and fail-closed key release. Done: `/v1/attestation` returns a real Intel TDX quote whose report-data binds a client nonce, gateway version/region, and pinned confidential-backend model revisions; fails closed when evidence is unavailable; documented client verification. Remaining: server-side quote verification/PKI, and binding a measured-boot model image digest rather than gateway-asserted config. |
| Security assurance | Partial | Egress restrictions, Binary Authorization enforcement, VPC Service Controls where applicable, restore/incident exercises, and an independent penetration test. Done: Binary Authorization with attestor-required image signing (KMS-signed release attestor, deny-by-default, drilled unsigned-denied/signed-allowed), egress restrictions on model pods (default-deny plus HuggingFace-only FQDN allowlist, drilled), and recurring restore/failover/rollout/Redis drills. Remaining: VPC Service Controls and an independent penetration test (both owner/procurement decisions). |

## Global acceptance tests

1. No prompt, completion, raw API key, authorization header, wallet grant, or Basic-auth credential appears in logs, metrics, traces, audit exports, or backups.
2. A confidential request never silently downgrades, including during zone loss, rollout, quota exhaustion, or attestation failure.
3. Revocation, spend enforcement, and abuse controls remain effective under concurrent requests and regional failover.
4. A release and a model rollout can each be rolled back without changing customer endpoint or credentials.
5. Recovery point and recovery time objectives are measured by recurring restore and failover drills rather than documentation alone.
